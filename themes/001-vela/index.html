What you stop building

Four systems you no longer have to own.

Every team that ships background work rebuilds the same four things, badly, under deadline. Vela ships them as primitives.

Durable retries

Exponential backoff, jitter, and a dead-letter queue that is queryable rather than a dumping ground. A step that fails on attempt four resumes from attempt four, not from the beginning.

Step-level traces

Every run is a tree of steps with inputs, outputs, duration and the exact exception. You stop reading log lines to work out which of nine stages hung.

Schedules, no cron box

Cron expressions and calendar rules with timezone and DST handled properly. No box whose only job is cron, no 3am page because that box rebooted.

Idempotency by default

Pass a key, get exactly-once semantics for the window you choose. The double-charge class of bug stops being yours to prevent by hand.

How it works

A workflow is a function. Durability is the runtime’s problem.

  1. Define steps. Each step.run is checkpointed. Its result is persisted before the next one starts.
  2. Sleep without holding a process. step.sleep for a minute or a fortnight; nothing of yours stays resident.
  3. Deploy anywhere. The SDK is a dependency, not a daemon. It runs on your serverless functions, containers or a laptop.
  4. Watch it, then forget it. Traces, alerts and replay are on by default rather than a later integration.
workflows/dunning.tsTypeScript
// Retries, sleeps and replays are handled by the runtime.
export const dunning = vela.workflow({
  id: "invoice.dunning",
  retries: 5,
}, async ({ step, event }) => {
  const invoice = await step.run("load", () =>
    db.invoices.find(event.invoiceId));

  for (const day of [3, 7, 14]) {
    await step.sleep(`wait-${day}d`, `${day}d`);
    if (await step.run("paid?", () => isPaid(invoice)))
      return { settled: true, day };

    await step.run(`remind-${day}d`, () =>
      email.send(invoice.contact, "reminder", { day }));
  }

  return step.run("escalate", () => collections.open(invoice));
});

Questions

The ones we actually get asked.

Do I have to run a worker?

No. The SDK registers your workflows and Vela calls them over HTTPS, so your existing serverless functions or containers are the workers. There is nothing new to keep alive.

What happens if my function is redeployed mid-run?

Completed steps are already persisted, so the run resumes at the next uncompleted step against the new deployment. Long sleeps are held by us, not by your process, so a deploy during a fourteen-day wait is a non-event.

Can I migrate off?

The workflow definitions are ordinary functions in your repository. Export your run history as newline-delimited JSON at any time, including on the free tier.

Where does my data live?

In the region you pick at project creation, and it does not leave it. Step inputs and outputs can be encrypted with your own key, in which case we store ciphertext and traces show shapes rather than values.
